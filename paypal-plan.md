# PayPal plan: the second reading of a capture

Written with the APIMatic Context Plugin for PayPal (`paypal@context-plugins`, installed with
`npx context-plugins install paypal`). Its TypeScript workflow asks for a contract sheet before code, and this is
that sheet for the one operation the Guardian reads twice.

## Scope

When the Guardian reconciles a captured payment, it reads the capture a second time and compares it with what the
app's own client recorded (`src/paypal/sdk-reader.ts`, used by `POST /api/proposals/:id/reconcile`).

| In scope | Out of scope |
|---|---|
| `GET /v2/payments/captures/{capture_id}` (read only) | Creating, capturing, voiding or refunding. Those stay in `src/paypal/client.ts` |

## Which SDK, and why it is not the plugin's own

The plugin documents a TypeScript SDK named `paypal`. It is **not published to npm**: it is built from
`github.com/context-plugins/paypal-typescript-sdk`. Making that a dependency of this repository would make
`npm install` (for the judges and for Render) depend on a Git build, so the reader uses PayPal's official,
registry-published `@paypal/paypal-server-sdk` 2.5.0 (also generated by APIMatic) instead. The plugin's map is used
for the contract facts below; the 2.5.0 type definitions were read for the names that package uses.

## Host decision

One host: the PayPal Sandbox. `Environment.Sandbox` is fixed in code, and `sdkReaderFromEnv` returns nothing when
`PAYPAL_BASE_URL` is not a sandbox URL, so a production base URL can never produce a reader. The credentials are the
Sandbox app's, from the environment. Nothing is hardcoded.

## Contract sheet: `getCapturedPayment`

| Fact | Value | Source |
|---|---|---|
| Plugin SDK signature | `getCapturedPayment(request: Payments.GetCapturedPaymentRequest, options?): ApiPromise<CapturedPayment, Payments.GetCapturedPaymentError>` | plugin map, `map/operations/payments.md` |
| Signature in the SDK this repo uses | `PaymentsController.getCapturedPayment({ captureId, paypalMockResponse? })` | `@paypal/paypal-server-sdk` 2.5.0 types |
| Wire | `GET /v2/payments/captures/{capture_id}`, no body | plugin map |
| Auth | OAuth 2 client credentials; token at `/v1/oauth2/token` | plugin map |

Request fields

| Field | Channel | Wire name | Required | Set it? |
|---|---|---|---|---|
| `captureId` | path | `capture_id` | yes | yes, the capture id the app recorded |
| `payPalMockResponse` | header | `PayPal-Mock-Response` | no | **no.** It is PayPal's negative-testing header, and nothing here needs it |

Response members used (`CapturedPayment`): **every member is optional** in the schema, none is nullable.

| Member (SDK name / wire name) | Used for | If absent |
|---|---|---|
| `status` / `status` | must be `COMPLETED` | the reading is **unavailable**, not a disagreement |
| `amount.value`, `amount.currencyCode` / `amount.value`, `amount.currency_code` | compared with what the app recorded | the reading is **unavailable** |
| `supplementaryData.relatedIds.orderId` / `supplementary_data.related_ids.order_id` | compared with the order the app holds | not compared (PayPal does not always return it) |

`CaptureStatus` is an open enum: `COMPLETED`, `DECLINED`, `PARTIALLY_REFUNDED`, `PENDING`, `REFUNDED`, `FAILED`. An unknown
value is kept as it came and reads as "not COMPLETED".

Because every member is optional, a thin or truncated `2xx` decodes without complaint. The reader therefore asserts on
`status` and `amount` itself and reports an unavailable reading instead of letting a missing field look like agreement
or like an alert.

## Errors: when the API says no

The operation declares typed arms for 401, 403, 404, 500 and a default. The reader does not branch on the arm tag; it
keeps only the status.

| Status | What the record says | Counts as a disagreement? |
|---|---|---|
| 401 / 403 | "PayPal refused this app's credentials" (ours, not the buyer's) | no, the reading is unavailable |
| 404 | "PayPal has no capture with this id" | no, the reading is unavailable |
| 429 / 5xx | "PayPal answered N" | no, unavailable |
| no response (connection or timeout) | the SDK's message | no, unavailable |

A failed second reading never changes the verdict by itself. Only a readable capture that differs from the app's own
reading raises an alert.

## Durable writes, duplicate claims, unknown outcomes, cross-operation invariants

None. The operation is a read: it creates nothing, so there is no claim to store, no outcome to settle and no value
whose legal set another operation defines.

## Resilience and logging

- The client is built once at startup (`server.ts`) and held, so the OAuth token cache lives for the process.
- A read is safe to repeat, and the SDK's own retry policy applies. The per-request timeout is 15 s.
- Logging is off. Nothing from a request or response body is logged.

## Tests

`test/sdk-reader.test.ts` covers the comparison, the thin-body rule, the error messages and the Sandbox-only guard.
`test/paypal.test.ts` covers the three outcomes through the reconcile route: agrees, disagrees (alert), unavailable.

## Assumptions and blockers

- **Verified against a real capture of this app's own Sandbox account on November 9, 2026**, on the public Render
  deployment: a USD 17.99 capture was read through the SDK and the detail window reported "Second reading (PayPal SDK):
  agrees" (17.99 USD, `COMPLETED`). Before that, the SDK had authenticated and reached PayPal (a nonexistent capture
  answers 404). The capture ids in `docs/SANDBOX-RESULTS.md` belong to another Sandbox app and answer 401 with this
  app's credentials, which is why the check needed a capture made by this app.
- `order_id` inside `related_ids` is typed in the SDK this repo uses, but the plugin's map entry for it was not
  opened, so that comparison rests on the 2.5.0 types alone.
